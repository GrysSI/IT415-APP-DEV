# Evidence and Submission Checklist

Use this checklist to audit or prepare a submission. Mark an item verified only after inspecting the corresponding evidence. Leave instructor-only fields and unknown results blank.

## Application behavior

- [ ] Application runs from the documented steps.
- [ ] Interface is touchscreen-oriented and has large item controls.
- [ ] At least six products and their prices are visible.
- [ ] Select, increase, decrease, and remove operations work.
- [ ] Item subtotals and total are correct.
- [ ] Order summary is present and Back permits modification.
- [ ] Cash, QR simulation, and card simulation are available.
- [ ] Invalid or insufficient cash is rejected with clear feedback.
- [ ] Cash change is correct.
- [ ] Successful payment shows a unique transaction reference.
- [ ] Receipt details and payment method are correct.
- [ ] New Transaction clears prior state and starts a fresh transaction.

## Repository and workflow

- [ ] Shared repository URL is recorded and accessible to the intended reviewer.
- [ ] Local clone can be demonstrated.
- [ ] Files are organized and tracked with Git.
- [ ] History shows genuine setup, interface, core logic, validation, bug fix, refactoring, and documentation stages.
- [ ] Commit messages are meaningful and authorship is identifiable.
- [ ] Each member's GitHub identity, assigned work, and feature branches are recorded.
- [ ] Branch work was pushed and appears in pull requests targeting the integration branch.
- [ ] Review evidence exists before merge.
- [ ] Requested changes, when present, were addressed and documented.
- [ ] Completed feature work is merged.
- [ ] The demonstrated application matches the recorded final commit.

## AI-development evidence

- [ ] At least one sufficiently detailed generation prompt and response are recorded.
- [ ] A real debugging case records the error, prompt, response, applied fix, and verification.
- [ ] A real refactoring case records the original concern, improvement, and regression verification.
- [ ] Every entry identifies the responsible member.
- [ ] Each entry evaluates the AI output and describes human modifications.
- [ ] Related files, commits, pull requests, tests, or screenshots are referenced when available.

## Code quality

- [ ] Modules or files have clear responsibilities.
- [ ] Repeated logic is reused rather than copied.
- [ ] Business logic is separated from UI/DOM code where practical.
- [ ] Validation handles blank, malformed, negative, and insufficient inputs.
- [ ] Totals, amount due, change, success details, and receipt values share one calculation source.
- [ ] Relevant automated and manual checks are recorded with actual outcomes.

## Documentation

- [ ] README explains setup, dependencies, run steps, technology, storage, and contributions.
- [ ] AI development log includes prompts, useful response summaries, evaluations, modifications, verification, and attribution.
- [ ] Member register includes names, usernames, branches, tasks, commits, pull requests, reviewers, and merge status.
- [ ] Evidence index points each criterion to an exact repository file, URL, commit, pull request, test, or figure.
- [ ] Acceptance checks reflect observed behavior rather than planned behavior.
- [ ] Unverified instructor decisions remain blank.

## Per-member verification record

For each member, record Verified, Missing/Incorrect, or Not Applicable for:

- GitHub identity.
- Feature branch and assigned work.
- Meaningful authored commits.
- Pushed branch changes.
- Pull-request ownership and feature changes.
- Review and merge evidence.
- AI generation, debugging, and refactoring evidence.
- Evaluation and adaptation of AI output.
- Ability to explain and demonstrate the contribution.

Commit count alone does not prove authorship or contribution. Use commit details, diffs, pull-request records, reviews, and the member's explanation together.
