# IT415 POS Four-Stage Workflow

Use one four-stage cycle for every substantive request about the IT415 touchscreen POS kiosk project:

1. Understand the request and applicable requirements.
2. Plan the smallest traceable solution.
3. Implement the requested work.
4. Verify the result and record honest evidence.

Read [references/four-stage-prompt-cycle.md](references/four-stage-prompt-cycle.md) before beginning a cycle. Keep all four stages visible in the work, but scale each stage to the request. For a review or planning request, Stage 3 produces the requested analysis or plan rather than changing files.

## Operating rules

- Treat repository state and user-provided facts as the source of truth. The source PDF contains one completed submission whose names, URLs, branches, commits, pull requests, test counts, and check marks are examples, not reusable facts.
- Never invent evidence, claim an unrun test passed, pre-check an unverified item, or create artificial commits to satisfy a history requirement.
- Preserve the user's existing work and assigned scope. Do not commit, push, open or merge pull requests, deploy, or edit external systems unless the user requests that action.
- Keep application logic modular: separate business calculations and validation from DOM/UI behavior where the project structure supports it.
- Use one calculation path for order totals, payment amount, change, success details, and receipts so the displayed values cannot silently diverge.
- When AI-assisted work is part of the assignment record, document the prompt purpose, useful response, human evaluation, adaptations, responsible member, verification, and related code evidence.
- End each completed cycle with a concise result covering the four stages, tests or checks actually performed, evidence created or updated, and any unresolved item.
